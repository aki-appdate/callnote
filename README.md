# CallNote — テレアポチームのAI営業アシスタント

[![CI](https://github.com/aki-appdate/callnote/actions/workflows/ci.yml/badge.svg)](https://github.com/aki-appdate/callnote/actions/workflows/ci.yml)

架電メモをAIが整理し、**次の一手**と**チームの改善点**を見える化するWebアプリです。
テレアポのオペレーターとSV（現場リーダー）を経験した筆者が、現場で感じた課題をもとに作りました。設計・仕様決め・動作確認は筆者、実装は Claude Code（AIコーディングツール）です。

> デモ版です。会社名・人名・電話番号などのデータはすべて架空です。ログイン不要で、誰でも試せます。

## 解決したい課題

| 現場の困りごと | CallNote でやること |
|---|---|
| 電話の直後にCRMへ細かく入力するのが重く、架電の手が止まる | 結果を1クリックで選び、メモは走り書きでOK。要約・温度感・断りの理由・次回日をAIが整理 |
| 次にいつ・何を話すかが担当者の頭の中にしかない | 「次に電話する日」と「次に話すこと」を記録し、当日の架電リストに自動で並べる |
| SVが、誰がどこでつまずいているかを把握しにくい | メンバー別の接続率・受付止まり・アポ率、断り理由の内訳を集計。AIが根拠の記録つきで気づきを出す |

## 主な機能

**メンバー画面（/calls）**
- 今日かける案件の一覧（予定日が来たフォローは全件、そのあとに新規を「1日50件の目安 − 今日かけた件数」まで。予定日を過ぎたものは赤で表示）
- 電話の結果（6種類）＋メモ → 「AIで整理する」
- AIの提案を**人が確認・修正してから保存**。AIが判断しきれない点は「人が確認してほしいこと」として目立たせる
- 書き換えた項目は「人が修正」として記録に残し、あとでAIの精度を振り返れる
- 「次に電話する日」を空欄で保存すると、その案件は「見送り」になり、今日かける一覧から外れる
- 「AIを使わずに保存」したときは、結果ごとの標準の間隔（不在なら翌営業日、受付止まりなら2営業日後など）で次回を入れる

**SVダッシュボード（/sv）**
- 今日／今週／直近2週間の切り替え（月曜の朝など「今週」の架電が30件未満なら、最初は直近2週間で表示）
- 集計欄（アポ数・アポ率・架電数・担当者接続率・予定日を過ぎたフォロー）と、予定日を過ぎたフォローの一覧（古い順に5件、残りは開いて全件）
- メンバー別の表（平均より受付で止まりがちな人に印）
- 断り理由の内訳（担当者と話せた・お断りの電話だけを数える。受付止まりや不在は数えない）、日ごとの架電数
- 「朝会メモ」：AIが気づき最大3つと打ち手を下書き。**気づきごとに、もとにした架電ログの行を抜き出し、決め手の言葉に線を引いて見せる**（押すと全文）。期間の架電が30件未満なら結論を出さず「記録が少なめ」とだけ伝える
- 根拠の記録の要約は、デモデータなら「見本の返答で自動作成・人の確認なし」、利用者が保存した記録なら「人が確認して保存」と書き分ける

## AIの使い方で気をつけたこと

1. **人が最後に決める**：AIの出力は「提案」として表示し、確認ボタンを押すまで保存しません。
2. **返答の形を固定する**：zod で定義した型から JSON Schema を作って Gemini に渡し（構造化出力）、受け取った値も同じ zod で検証します。形が違えば使いません。
3. **作り話を防ぐ**：チーム分析では、AIが挙げた根拠の記録IDが実在するかを確かめ、根拠のない気づきは捨てます。過去の日付が提案されたら日付を空にして、人に確認を求めます。
4. **止まらない**：AIが使えないとき（未設定・無料枠の上限・通信エラー・形の不正）は、ルールベースの「見本の返答」に自動で切り替えます。画面上部の表示で、どちらが動いたか分かります。
5. **使いすぎを防ぐ**：Firebase App Check（reCAPTCHAのキーを設定したとき）でこのサイト以外からの呼び出しを防ぎ、ブラウザごとに1日のAI利用回数（30回）を区切っています。

AIが使えないときの「見本の返答」はルールベースです。メモの言葉から断りの理由・温度感・次回日（「来週の水曜」「2〜3日後」「明日」「来年の3月」「3月末」など。土日・祝日・年末年始（12/29〜1/3）は次の営業日へ）を読み取ります。「満了は来年の3月」のように契約の満了時期が書いてあれば、満了日ではなく満了の2〜3か月前を次回日にし、「満了の2〜3か月前に比較見積を提案」と返します。祝日は2026〜2027年の固定の表で持っています（ライブラリは使っていません）。見本の返答でも、同じ人を「受付で止まりがち」と「アポ率が高い」の両方で挙げないなど、気づき同士が食い違わないようにしています。

## 技術構成

| 分野 | 使ったもの |
|---|---|
| 画面 | Next.js 16（App Router）/ React 19 / TypeScript / Tailwind CSS 4 |
| データ保存 | Cloud Firestore（匿名認証で一人ずつ分離）。未設定時はブラウザの localStorage |
| AI | Firebase AI Logic + Gemini（Gemini Developer API の無料枠・Spark プラン） |
| セキュリティ | Firestore セキュリティルール（[firestore.rules](firestore.rules)）、App Check（reCAPTCHA v3） |
| 品質 | Vitest（単体テスト）、ESLint、GitHub Actions（push・PRで lint・型・テスト・ビルドを走らせる設定） |
| 公開 | Vercel（予定） |

```
src/
├─ app/                 画面（/ 紹介、/calls メンバー、/sv SV）
├─ components/          画面の部品
└─ lib/
   ├─ ai/               AI呼び出し（gemini.ts）、指示文（prompts.ts）、見本の返答（sample.ts）
   ├─ store/            保存先（Firestore と localStorage を同じ窓口で切り替え）
   ├─ kpi.ts            SV画面の数字の計算
   ├─ worklist.ts       メンバーの「今日かける」一覧の作り方
   ├─ dates.ts          日付・営業日（祝日の表）
   ├─ schemas.ts        AIの返答の型（zod）
   └─ seed.ts           架空のデモデータ
```

### データの持ち方の工夫

デモデータ（架空の2,600社・メンバー4人の過去2週間ぶんの架電記録 約2,000件）は、乱数の種を固定した関数で、開くたびに「今日」を基準に作り直します。
何日後に開いても「今日の架電がある」「予定日を過ぎたフォローが十数件」という同じ状態になり、データが古びません。土日・祝日・年末年始には電話をかけない前提で作ります。

数字は法人向けテレアポ（OA機器・法人携帯）の現場感に合わせています。

| 項目 | デモデータの値（直近2週間） |
|---|---|
| 1人1日の架電数 | 約50件（40〜60件） |
| 担当者接続率 | 約22%（15〜25%） |
| アポ率（架電数に対して） | 約3%（2〜4%） |
| 1人1日のアポ数 | 約1.4件（1〜2件） |
| 予定日を過ぎたフォロー | 十数件 |

保存するのは「利用者が追加した記録・案件の変更」だけで、利用者の記録は保存した日時のまま重ねます。保存1回あたりの書き込みは2件（記録1件＋案件の変更1件）で、無料枠で運用できるようにしています。
Firestore のルールでは、記録の項目名・型・長さ（「次に話すこと」「確認してほしいこと」は中の1つずつの型と文字数まで）を決められた範囲に制限し、記録の書き換えは禁止しています（[firestore.rules](firestore.rules)）。

## 手元で動かす

```bash
npm install
npm run dev        # http://localhost:3840
npm run check      # lint・型チェック・テスト
```

Firebase を使う場合は `.env.example` を `.env.local` にコピーして値を入れます。空のままでも、ブラウザ内保存＋見本の返答で全機能を試せます。

## 開発の進め方

- 設計・仕様決め・動作確認は筆者が行い、実装は Claude Code に任せています。プロジェクトのルールは [CLAUDE.md](CLAUDE.md) にまとめています。
- AIが書いたコードは、テスト・型チェック・ブラウザでの操作確認の3つで確かめています。
- レビュー役のAIに不具合・説明とのずれを洗い出させ、見つかった点を直してテストを足す、という流れで改善しています。
